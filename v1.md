# V1 — Customer Ride Application

**Project:** Customer-side ride application  
**Backend:** Spring Boot  
**Frontend:** React Native  
**V1 Deadline:** **24 September 2026**  
**Plan Start:** 10 September 2026  
**Primary Goal:** Build a production-quality customer application in which a customer logs in with a phone number, selects/searches their work location on a map, and creates a ride/request that is discoverable within a 4 km radius of the selected location.

---

# 1. V1 Objective

The first version should prove the complete customer journey:

```text
Open App
   ↓
Phone Number Login
   ↓
OTP Verification
   ↓
Customer Profile
   ↓
Map / Location Search
   ↓
Select Work Location
   ↓
Create Ride
   ↓
Ride Stored in Backend
   ↓
Ride Discoverable within 4 km
   ↓
Customer Can View / Manage Own Ride
```

The goal is **not** to build every possible feature.

The goal is to build a small but professionally engineered foundation that can be extended later into a full-scale ride/delivery platform.

# 2. V1 Scope

## 2.1 Customer Features

### Authentication
- Enter phone number.
- Request OTP.
- Verify OTP.
- Create/login customer account.
- Persist authenticated session.
- Logout.
- Basic authentication error handling.

### Customer Profile
- Customer ID.
- Phone number.
- Optional display name.
- Created timestamp.
- Updated timestamp.

### Map
- Display interactive map.
- Request location permission.
- Show customer's current location.
- Search for a location/address.
- Select a location on the map.
- Move map marker / pin.
- Confirm selected work location.
- Store latitude and longitude.
- Store a human-readable address where available.

### Ride Creation
Customer can create a ride using the selected work location.

Minimum ride information:

- Pickup/work latitude.
- Pickup/work longitude.
- Address.
- Optional title/description.
- Ride status.
- Created timestamp.

Recommended initial status:

```text
ACTIVE
```

### Nearby Ride Discovery

A customer can retrieve rides whose location is within:

```text
4 km
```

of a selected/current location.

The backend must perform the radius calculation.

**Do not rely only on the React Native application to filter rides.**

The backend is the source of truth.

### My Rides
Customer can:
- View their rides.
- View ride details.
- See ride status.
- Cancel/deactivate their own active ride.

```text

                         |
        +----------------+----------------+
        |                |                |
        ↓                ↓                ↓

     Module           Module          Module
```

# 7. Database Design

Use PostgreSQL.

## 7.1 customers

```text
customers
--------------------------------
id                  UUID PK
phone_number        VARCHAR UNIQUE
name                VARCHAR NULL
created_at          TIMESTAMP
updated_at          TIMESTAMP
```

Phone number should be normalized before storage.

Example:

```text
+919876543210
```

Do not store the same user as:

```text
09876543210
+91 98765 43210
98765-43210
```

---

## 7.2 rides

```text
rides
--------------------------------
id                  UUID PK
customer_id         UUID FK
latitude            DECIMAL / spatial type
longitude           DECIMAL / spatial type
address             VARCHAR
title               VARCHAR NULL
description         TEXT NULL
status              VARCHAR
created_at          TIMESTAMP
updated_at          TIMESTAMP
```

Recommended status:

```text
ACTIVE
CANCELLED
COMPLETED
```

V1 may initially use only:

```text
ACTIVE
CANCELLED
```

---

## 7.3 OTP

Do not store raw OTPs permanently.

A production implementation should use an OTP provider where possible.

If OTP is temporarily implemented internally for development:

```text
otp_verifications
--------------------------------
id                  UUID PK
phone_number        VARCHAR
otp_hash            VARCHAR
expires_at          TIMESTAMP
attempt_count       INTEGER
verified_at         TIMESTAMP NULL
created_at          TIMESTAMP
```

OTP must expire.

OTP attempts must be rate-limited.

# 8. Location Strategy

This is one of the most important architectural decisions.

The mobile application can obtain:

```text
latitude
longitude
```

The backend receives the coordinates.

The backend is responsible for:

- validating coordinates,
- storing them,
- finding nearby rides,
- enforcing the 4 km radius.

Do not calculate business-critical proximity only on the phone.

---

# 9. Geospatial Queries

For V1, PostgreSQL should preferably use **PostGIS** if available.

This gives us proper spatial indexing and distance queries.

Conceptually:

```text
Customer location
       |
       ↓
latitude + longitude
       |
       ↓
PostGIS distance query
       |
       ↓
rides within 4 km
```

The query should conceptually mean:

```text
Find ACTIVE rides
WHERE distance(ride_location, requested_location) <= 4000 meters
```

Add a spatial index so this remains efficient as the number of rides grows.

If PostGIS is not used initially, a Haversine-based implementation can work for a small prototype, but the production-oriented V1 should prefer a spatial database approach.

## Nearby Rides

```http
GET /api/v1/rides/nearby?latitude=28.6139&longitude=77.2090&radiusKm=4
```

The server should validate the radius.

For V1, do not allow arbitrary huge radius values.

Example rule:

```text
0 < radius <= 4 km
```

or simply expose:

```http
GET /api/v1/rides/nearby?latitude=...&longitude=...
```

and keep 4 km as a backend business constant.

Response:

```json
{
  "rides": [
    {
      "id": "...",
      "latitude": 28.6150,
      "longitude": 77.2080,
      "address": "...",
      "title": "Office Ride",
      "status": "ACTIVE",
      "distanceMeters": 180
    }
  ]
}
```

Returning `distanceMeters` is useful for sorting and displaying proximity.

# 13. API Response Standard

Do not let every endpoint return completely different structures.

For errors:

```json
{
  "timestamp": "2026-09-10T16:30:00Z",
  "status": 400,
  "code": "INVALID_REQUEST",
  "message": "Latitude must be between -90 and 90",
  "path": "/api/v1/rides"
}
```

Use a centralized exception handler:

```text
@RestControllerAdvice
```

Handle at least:

- Validation errors
- Authentication errors
- Authorization errors
- Resource not found
- Business rule violations
- Unexpected server errors

Never expose stack traces to mobile clients.

# 18. Authentication Security

Phone authentication is security-sensitive.

Minimum requirements:

- HTTPS only.
- OTP expiration.
- OTP attempt limit.
- OTP resend cooldown.
- Rate limiting on OTP requests.
- Do not log OTP values.
- Do not return OTP in API responses.
- Secure token storage on the device.
- Access-token expiration.
- Refresh-token rotation/revocation strategy.
- Server-side authorization on every protected resource.

For development, test OTP mechanisms can be used, but production credentials/secrets must never be committed to Git.

# 26. Critical Edge Cases

The application must handle:

### Location

- Location permission denied.
- GPS unavailable.
- Invalid coordinates.
- User manually searches for a location.
- User moves outside the selected area.
- No nearby rides.

### Authentication

- Wrong OTP.
- Expired OTP.
- OTP resend.
- Too many attempts.
- Network failure.
- Token expired.
- Refresh token failure.

### Ride

- Ride creation fails.
- Duplicate taps on Create Ride.
- User cancels an already cancelled ride.

- Ride does not exist.
- No nearby rides.
- Database failure.

```text
Loading
Success
Empty
Error

```

Never leave the user staring at a blank screen.

# 27. API Security Model

Public endpoints:

```text
POST /auth/otp/request
POST /auth/otp/verify
```

Protected endpoints:

```text
GET  /customers/me
PATCH /customers/me

POST /rides
GET  /rides/nearby
GET  /rides/me
GET  /rides/{id}
PATCH /rides/{id}/cancel
```

Every protected endpoint should identify the customer from the authenticated token.

Do not accept:

```json
{
  "customerId": "..."
}
```

from the mobile application as the authority for ownership.

Instead:

```text
JWT
 ↓
Authenticated Principal
 ↓
customerId
 ↓
Service
```

This prevents users from pretending to be another customer.

# 28. Performance Requirements

V1 does not need premature optimization.

But build the important foundations correctly:

- Database indexes.
- Spatial index for location queries.
- Pagination for lists.
- Server-side filtering.
- Proper connection pooling.
- Avoid N+1 queries.
- Do not return unnecessary columns/data.
- Avoid loading thousands of rides into the mobile app.
- Set reasonable API timeouts.

For nearby rides, use pagination or a sensible maximum result count.

```text
 ↓
```

For V1:

```text
Modular Monolith > Microservices
```

Use clean boundaries inside one application.

## Rule 3 — Production Thinking, Not Production Complexity

We want:

- Security
- Validation
- Testing
- Logging
- Migrations
- Clean architecture
- Good API design
- Proper database design

- Kafka everywhere
- Kubernetes
- Distributed tracing infrastructure
- Complex event sourcing

unless an actual requirement appears.
